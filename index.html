SpermaCore Plugin API

Справочник по C ABI для написания плагинов · версия 1.4

Обзор

SpermaCore — модульное ядро на Go + cgo. Вся функциональность агента реализуется через плагины — динамические библиотеки (.dll, .so, .dylib), которые загружаются во время выполнения.

Плагин ничего не знает о ядре кроме контракта, описанного в одном заголовочном файле include/plugin_api.h. Контракт стабилен, версионирован, и позволяет:

  • Предоставлять тулы для LLM (function calling)
  • Дописывать системный промт
  • Участвовать в интерактивном старте — задавать вопросы, показывать меню
  • Реагировать на события через хуки
  • Читать свои настройки из config.toml
  • Самостоятельно создавать свои секции в конфиге с дефолтами
  • Объявлять требования к ABI и зависимости от других плагинов
  • Сообщать о своём health для дашборда
  • Применять новый конфиг без перезапуска (hot-reload)
  • Писать в общий лог ядра — в том числе структурированный

Философия. Ядро — гость в мире плагинов. Оно не знает, что делает плагин. Оно только спрашивает: «что ты умеешь?», «чего тебе надо?» и «сделай вот это». Всё остальное — дело плагина.

Быстрый старт

Чтобы написать плагин, нужно три вещи:

  1. Создать папку modules/my_plugin/src/
  2. Положить туда my_plugin.c с реализацией
  3. Добавить имя в config.toml → [plugins] load

Ядро само найдёт исходник, соберёт через CMake и загрузит. Отдельная сборка не требуется.

Если плагину нужны настройки — он сам попросит ядро их создать через core->config_ensure() в init(). Юзеру не нужно знать заранее, какие ключи у плагина есть.

Версионирование ABI

ABI описывается двумя константами:

КонстантаЗначениеКогда меняется
SC_ABI_MAJOR 1 При ломающих изменениях — ядро отвергает несовместимые плагины
SC_ABI_MINOR 4 При добавлении полей в конец структур (обратно совместимо)

История версий

ВерсияЧто добавлено
1.0Базовый контракт: get_info, init, get_tools, call_tool, get_hooks
1.1Интерактив: prompt_yes_no, prompt_text, prompt_select, on_startup
1.2Системные промты: get_system_prompt
1.3Конфиг: config_get_string / int / bool / double, поле enabled
1.4Self-configuring plugins: config_ensure, требования (min_abi_*, requires), флаги, health, on_config_reload, is_plugin_loaded, now_ms, log_json, топосортировка, валидация, лимиты

Обратная совместимость. Все новые поля добавляются только в конец структур. Старые плагины продолжают работать без пересборки. Поле struct_size позволяет ядру понять, какие поля есть у плагина.

Старые плагины автоматически получают дефолты новых полей: min_abi = 1.0, flags = 0, requires = "", health = NULL, on_config_reload = NULL.

Core API

Структура sc_core_api_t — то, что ядро даёт плагину. Указатель приходит в init() и валиден до вызова deinit().

typedef struct sc_core_api { ... } sc_core_api_t;

Проверка версии. Методы, добавленные в 1.4, доступны только если core->abi_minor >= 4. Плагин обязан проверить перед вызовом:

if (g_core->abi_minor >= 4 && g_core->config_ensure) {
    g_core->config_ensure(...);
}

alloc / free

Выделение и освобождение памяти через аллокатор ядра.

void* (SC_CALL *alloc)(size_t size);
void (SC_CALL *free)(void* ptr);

Жёсткое правило. Всё, что плагин возвращает ядру и помечает флагом SC_PLUGIN_FLAG_OWNS_TOOL_RESULT — обязано быть выделено через core->alloc. Ядро освободит это само через core->free. Без флага ядро только читает строку, не пытаясь её освободить.

log / log_json

Запись в общий лог ядра. Идёт в data/logs/agent.log и (опционально) в дашборд.

void (SC_CALL *log)(int level, const char* name, const char* msg);
void (SC_CALL *log_json)(int level, const char* name, const char* msg_json) ABI 1.4;

Уровни — зеркало логгера ядра:

КонстантаЗначениеКогда использовать
SC_LOG_DEBUG0Отладка, детали
SC_LOG_INFO1Обычные события
SC_LOG_TOOL2Вызовы тулов
SC_LOG_WARN3Что-то подозрительное
SC_LOG_ERROR4Ошибки

log_json принимает валидный JSON-объект. Ядро парсит его и (в будущем) показывает поля в дашборде отдельными колонками. Сейчас пишет в лог как есть. Пример:

g_core->log_json(SC_LOG_INFO, "myplugin",
    "{\"event\":\"cache_hit\",\"key\":\"user_42\",\"latency_ms\":12}");

prompt_yes_no / prompt_text / prompt_select

Интерактивные запросы к пользователю во время старта. Работают только из init() и on_startup().

int (SC_CALL *prompt_yes_no)(const char* question, int default_value);
int (SC_CALL *prompt_text)(const char* q, const char* dflt, char* out, size_t outsz);
int (SC_CALL *prompt_select)(const char* q, const char* const* opts, int n, int dflt);
ФункцияВозврат
prompt_yes_no1 — да, 0 — нет, -1 — прерывание
prompt_text0 — ок, строка в out, -1 — ошибка
prompt_selectИндекс выбранного пункта, -1 — ошибка

config_get_string / int / bool / double ABI 1.3

Чтение своей секции [plugins.<name>] из config.toml. Работает только во время init(). После возврата из init указатели становятся недействительными.

const char* (SC_CALL *config_get_string)(const char* key, const char* default_value);
int (SC_CALL *config_get_int)(const char* key, int default_value);
int (SC_CALL *config_get_bool)(const char* key, int default_value);
double (SC_CALL *config_get_double)(const char* key, double default_value);

Если ключ не найден в секции — возвращается default_value. Если секции нет вообще — работает так же, все ключи берутся из дефолтов.

Вне init — возвращает NULL/дефолт. Если плагин вызовет config_get_* из call_tool, ядро вернёт дефолт и запишет WARN в лог. Значения нужно кэшировать у себя в init().

Внимание на строки. config_get_string возвращает указатель, живущий до конца init. Если нужно сохранить значение дольше — скопируйте его в свой буфер через strncpy или ручной цикл.

config_ensure ABI 1.4

Попросить ядро создать или дополнить секцию [plugins.<name>] в config.toml. Это то, что делает плагины самонастраивающимися: при первом запуске они сами добавляют свои дефолты в конфиг, а юзер потом видит готовую секцию и может её править.

int (SC_CALL *config_ensure)(const char* name, const char* defaults_json);
ПараметрЧто значит
nameИмя плагина. Должно совпадать с именем в plugin_info.name и с секцией [plugins.<name>]
defaults_jsonJSON-объект с дефолтными значениями: {"model":"qwen3","timeout":30,"debug":false}

Возврат:

КонстантаЗначениеЧто случилось
SC_CONFIG_EXISTS0Секция уже была, ничего не меняли
SC_CONFIG_CREATED1Секции не было — создали с дефолтами
SC_CONFIG_APPENDED2Секция была, но добавили недостающие ключи
SC_CONFIG_ERR-1Ошибка чтения/записи

Существующие ключи не перезаписываются. Если юзер поменял model = "llama3" — при следующем запуске плагина ядро увидит ключ, не тронет его. Комментарии в config.toml тоже сохраняются (append-only).

Работает только во время init(). Вне init — возвращает SC_CONFIG_ERR и пишет WARN.

is_plugin_loaded ABI 1.4

Загружен ли указанный плагин. Полезно, если плагин может работать «частично» без зависимости.

int (SC_CALL *is_plugin_loaded)(const char* name);

Возвращает 1 — загружен, 0 — нет. Например:

if (g_core->is_plugin_loaded("telegram")) {
    // умеем отправлять сообщения
} else {
    // работаем в ограниченном режиме
}

now_ms ABI 1.4

Монотонное время в миллисекундах от старта процесса. Для таймеров и измерения интервалов внутри плагина.

uint64_t (SC_CALL *now_ms)(void);

Не путать с time(NULL): now_ms не зависит от системных часов и не скачет при переводе времени.

Plugin API

Структура sc_plugin_api_t — то, что плагин даёт ядру. Возвращается из единственной экспортируемой функции plugin_get_api().

SC_EXPORT const sc_plugin_api_t* SC_CALL plugin_get_api(void);

Эта функция — единственный символ, который ядро ищет в .dll.

get_info обязательно

Возвращает указатель на статическую структуру с метаданными плагина.

const sc_plugin_info_t* (SC_CALL *get_info)(void);

Валидация ядром. Ядро проверяет: name не NULL, ≤ 64 символов, version ≤ 32 символов, struct_size не превышает размер структуры ядра. Если проверка не прошла — плагин отвергается с понятным логом.

init / deinit init обязателен

Вызывается один раз при загрузке и выгрузке плагина. Внутри init доступны config_get_*, config_ensure и prompt_*.

sc_status_t (SC_CALL *init)(const sc_core_api_t* core, const char* config_json);
sc_status_t (SC_CALL *deinit)(void);

config_json — содержимое секции [plugins.<name>] в виде JSON. Обычно не нужен — используйте config_get_*.

Гарантия deinit. Даже если init вернул ошибку, ядро вызовет deinit перед выгрузкой библиотеки — чтобы плагин мог освободить частично созданные ресурсы.

get_tools опционально

Возвращает JSON-массив описаний тулов в формате OpenAI function calling.

sc_status_t (SC_CALL *get_tools)(char** out_json);

call_tool опционально

Обработка вызова тула от LLM.

sc_status_t (SC_CALL *call_tool)(const char* tool_name, const char* args_json, char** out_json);

Таймаут. Ядро ждёт ответ не более 30 секунд. Если плагин не успел — вызов отменяется, в лог идёт SC_ERR_TIMEOUT, воркер продолжает работу. Не делайте долгих синхронных операций внутри call_tool.

Лимит размера. Результат обрезается до 1 МБ. Всё, что длиннее — теряется, в лог идёт WARN. Если нужно больше — сохраняйте в файл и возвращайте путь.

get_hooks опционально

Возвращает массив зарегистрированных хуков.

sc_status_t (SC_CALL *get_hooks)(const sc_hook_reg_t** out_hooks, size_t* count);

on_startup ABI 1.1

Вызывается один раз после загрузки всех плагинов. Здесь плагин может задать вопросы через core->prompt_*, проверить наличие зависимостей через is_plugin_loaded.

sc_status_t (SC_CALL *on_startup)(void);

get_system_prompt ABI 1.2

Возвращает текст, который ядро добавляет к системному промту LLM.

sc_status_t (SC_CALL *get_system_prompt)(char** out_text);

health ABI 1.4

Возвращает текущее состояние плагина для дашборда. Опционально — если NULL, дашборд показывает просто «загружен».

sc_status_t (SC_CALL *health)(char** out_json);

Ожидаемый JSON:

{
  "ok": true,
  "msg": "connected, 42 peers cached",
  "extra": { "queue": 3, "latency_ms": 120 }
}

Поле ok: false подсветит плагин красным в дашборде. Например, если соединение с внешним сервисом потеряно.

on_config_reload ABI 1.4

Ядро перечитало config.toml (например, по команде или SIGUSR1). Плагин может применить новые настройки без перезапуска.

sc_status_t (SC_CALL *on_config_reload)(const char* cfg_json);

cfg_json — свежая секция [plugins.<name>] в JSON. Если NULL — плагин перезапускается целиком (пока не реализовано, будет в следующих версиях).

Внутри reload работают config_get_*. Плагин может перечитать настройки теми же функциями, что и в init. Указатели живут до конца вызова on_config_reload.

Self-Configuring Plugins

Это главная фишка ABI 1.4. Плагин при первом запуске сам просит ядро создать свою секцию в config.toml с дефолтами. Юзер потом видит готовый конфиг и может его править, но плагин уже не сломается от отсутствия ключей.

Как это работает

  1. В init() плагин вызывает core->config_ensure("myname", "{...}").
  2. Ядро проверяет config.toml:
    • секции нет — создаёт с дефолтами;
    • секция есть, но чего-то не хватает — добавляет недостающие ключи;
    • всё есть — ничего не делает.
  3. Плагин читает config_get_* — получает то, что в конфиге (или дефолты, если юзер удалил ключ).

Пример

static sc_status_t init(const sc_core_api_t* api, const char* cfg_json) {
    g_core = api;

    // Просим ядро создать секцию, если её нет
    if (api->abi_minor >= 4 && api->config_ensure) {
        int rc = api->config_ensure("myname",
            "{\"model\":\"qwen3:4b\",\"timeout\":30,\"debug\":false}");
        if (rc == SC_CONFIG_CREATED) {
            api->log(SC_LOG_INFO, "myname",
                "created config section with defaults");
        }
    }

    // Теперь читаем — если юзер удалил ключ, получим дефолт
    const char* model = api->config_get_string("model", "qwen3:4b");
    int timeout = api->config_get_int("timeout", 30);
    int debug = api->config_get_bool("debug", 0);

    // ВАЖНО: скопировать строку, если нужно дольше init()
    snprintf(g_model, sizeof(g_model), "%s", model);
    g_timeout = timeout;
    g_debug = debug;

    return SC_OK;
}

Что увидит юзер

После первого запуска в config.toml появится:

# ==== auto-added by plugin: myname ====
[plugins.myname]
model = "qwen3:4b"
timeout = 30
debug = false

Правила

ПравилоЧто значит
Существующие ключи не перезаписываютсяЕсли юзер поменял model — значение остаётся
Недостающие ключи добавляютсяЕсли в секции не было timeout — добавится
Комментарии сохраняютсяЯдро пишет append-only, не перегенерирует файл целиком
Только в initВне init возвращает SC_CONFIG_ERR
Имя = секцияconfig_ensure("myname", ...) создаёт [plugins.myname]

Зачем это. Раньше юзер должен был вручную открыть документацию, узнать, какие ключи поддерживает плагин, вписать их в конфиг. Теперь достаточно запустить ядро — и все секции появятся сами, с разумными дефолтами. Юзер только правит то, что хочет поменять.

Требования

ABI 1.4 добавил в sc_plugin_info_t поля, которые позволяют плагину объявить свои требования к ядру и к другим плагинам. Ядро проверяет их до загрузки — до вызова init, чтобы не тратить ресурсы впустую.

Поле requires

CSV имён плагинов-зависимостей. Если хотя бы одна не загружена — плагин пропускается с понятным логом.

const char* requires; // "telegram,embedsc"

Пример:

static const sc_plugin_info_t info = {
    .name = "myreact",
    .version = "1.0.0",
    .description = "Reactions wrapper",
    .capabilities = NULL,
    .min_abi_major = 1,
    .min_abi_minor = 4,
    .flags = SC_PLUGIN_FLAG_THREAD_SAFE,
    .requires = "telegram",   // не загрузится без telegram
};

Топосортировка

Раньше порядок загрузки плагинов определялся порядком в [plugins].load — если react стоял до telegram, он не находил транспорт. Теперь ядро само сортирует по зависимостям.

Пример: load = ["react", "usersc", "telegram"], и react.requires = "telegram". Ядро:

  1. Загрузит usersc и telegram (у них нет зависимостей).
  2. Потом react, потому что его зависимость уже загружена.

Циклические зависимости. Если A требует B, а B требует A — ядро логирует ошибку и грузит оба в порядке объявления. Плагины должны сами пережить, что зависимость ещё не готова.

Флаги

Битовые флаги поведения. Складываются через |.

ФлагЗначениеЧто значит
SC_PLUGIN_FLAG_THREAD_SAFE 1 << 0 call_tool можно звать параллельно. Без флага ядро сериализует вызовы через мьютекс
SC_PLUGIN_FLAG_OWNS_TOOL_RESULT 1 << 1 Плагин возвращает malloc-строку, ядро освободит её через core->free
SC_PLUGIN_FLAG_NO_HOT_RELOAD 1 << 2 Плагин не поддерживает hot-reload конфига
SC_PLUGIN_FLAG_REQUIRES_NETWORK 1 << 3 Hint для capability-based security (пока не enforced)

Осторожно с THREAD_SAFE. Флаг отключает мьютекс ядра. Если внутри call_tool плагин использует глобальные переменные без своей синхронизации — будут гонки. Либо используйте _Thread_local, либо свои мьютексы, либо не ставьте флаг.

OWNS_TOOL_RESULT и обратная совместимость. Плагины ABI ≤ 1.3 возвращают указатели на статические буферы — их нельзя освобождать. Ядро проверяет флаг: если он не выставлен, строка только читается через C.GoString и не free.

Безопасность

ABI 1.4 добавил несколько защит от кривых плагинов. Ядро больше не падает от одного бага — плохой плагин отвергается или ограничивается.

Валидация при загрузке

struct_size <= sizeof(plugin_api_t)Плагин отвергается (структура больше, чем ожидает ядро — несовместимо)
info.name != NULL и ≤ 64 символовОтвергается с логом
info.version ≤ 32 символовОтвергается
init != NULL после initОтвергается
call_tool != NULL если get_tools возвращает непустой массивОтвергается
min_abi_minor <= core->abi_minorПропускается (не отвергается)
requires все загруженыПропускается с логом

Capability whitelist

В конфиге плагина можно ограничить, какие syscall-методы ему разрешены. Если поля нет — все разрешены (для обратной совместимости).

[plugins.embedsc]
enabled = true
model = "qwen3-embedding:latest"
allow_syscalls = ["embedsc.*", "tg.get_user"]

[plugins.telegram]
enabled = true
allow_syscalls = ["tg.*"]

Плагин-калькулятор не сможет случайно дёрнуть tg.send_message в чат твоей мамы. Если попытается — получит SC_ERR_FORBIDDEN, в лог пойдёт WARN с именем плагина и методом.

Маски. tg.* матчит все методы с префиксом tg.. * матчит всё. Точное имя матчит только себя.

Конфигурация

Каждый плагин настраивается через секцию [plugins.<name>] в config.toml. Ядро парсит все такие секции и передаёт каждому плагину его собственную — как JSON в init(), а также делает доступной через config_get_*.

Поле enabled

В любой секции можно поставить enabled = false — плагин будет пропущен при загрузке, но останется в [plugins] load. Удобно для быстрого включения/выключения без правки списка.

По умолчанию. Если секции нет или поля enabled нет — плагин считается включённым.

Пример

# Список плагинов для загрузки (порядок не критичен — ядро топосортирует)
[plugins]
load = ["sysprompt", "remembrance", "telegram", "time"]

# --- Модуль telegram ---
[plugins.telegram]
enabled = true
session_name = "agent"
typing_speed_min = 200
typing_speed_max = 400
allow_syscalls = ["tg.*"]

# --- Модуль time ---
[plugins.time]
enabled = true

Внутри init() плагина telegram:

const char* s = g_core->config_get_string("session_name", "agent");
int v = g_core->config_get_int("typing_speed_min", 200);

s будет "agent", v будет 200 — значения взяты из конфига.

Тулы

Тул — это функция, которую LLM может вызвать сама. Ядро получает описания от всех плагинов, склеивает их в один массив и передаёт модели.

Формат описания

JSON-массив в формате OpenAI function calling. Каждый тул — объект с полями name, description, parameters.

Обработка вызова

Когда модель решает вызвать тул, ядро находит плагин-владелец по имени и вызывает его call_tool(). Если два плагина заявили одно имя — побеждает первый по порядку загрузки.

Таймаут 30 секунд. Если call_tool не успел — вызов отменяется, модель получает {"error":"timeout"} в качестве результата. Не делайте долгих синхронных HTTP-запросов внутри call_tool без своего таймаута.

Примеры

Плагин с тулом

Минимальный плагин, который предоставляет один тул.

#include "plugin_api.h"
#include <string.h>

static const sc_core_api_t* g_core = NULL;

static const sc_plugin_info_t* get_info(void) {
    static const sc_plugin_info_t info = {
        .name = "hello",
        .version = "1.0.0",
        .description = "Example plugin",
        .capabilities = NULL,
        .min_abi_major = 1,
        .min_abi_minor = 4,
        .flags = SC_PLUGIN_FLAG_THREAD_SAFE,
        .requires = "",
    };
    return &info;
}

static sc_status_t get_tools(char** out) {
    if (!out) return SC_ERR_INVALID_ARG;
    static const char* tools =
        "[{\"name\":\"hello\","
        "\"description\":\"Say hello\","
        "\"parameters\":{\"type\":\"object\",\"properties\":{},"
        "\"required\":[]}}]";
    *out = (char*)tools;
    return SC_OK;
}

static sc_status_t call_tool(const char* name,
                            const char* args,
                            char** out) {
    if (!name || !out) return SC_ERR_INVALID_ARG;
    *out = NULL;
    if (strcmp(name, "hello") != 0) return SC_ERR_NOT_FOUND;

    static char buf[64];
    snprintf(buf, sizeof(buf), "{\"status\":\"ok\"}");
    *out = buf;
    return SC_OK;
}

static sc_status_t init(const sc_core_api_t* api, const char* cfg) {
    (void)cfg;
    g_core = api;
    if (api->log) {
        api->log(SC_LOG_INFO, "hello", "initialized");
    }
    return SC_OK;
}

static sc_plugin_api_t g_api = {
    SC_ABI_MAJOR, SC_ABI_MINOR, sizeof(sc_plugin_api_t),
    get_info, init, NULL, NULL, get_tools, call_tool,
    NULL, NULL,   // on_startup, get_system_prompt
    NULL, NULL,   // health, on_config_reload (ABI 1.4)
};

SC_EXPORT const sc_plugin_api_t* SC_CALL plugin_get_api(void) {
    return &g_api;
}

Самонастройка

Полный пример плагина, который сам создаёт секцию в конфиге.

static sc_status_t init(const sc_core_api_t* api, const char* cfg_json) {
    g_core = api;
    (void)cfg_json;

    // 1. Просим ядро создать секцию с дефолтами (только ABI 1.4+)
    if (api->abi_minor >= 4 && api->config_ensure) {
        int rc = api->config_ensure("myplugin",
            "{\"model\":\"qwen3:4b\",\"timeout\":30,\"debug\":false}");
        switch (rc) {
            case SC_CONFIG_CREATED:
                api->log(SC_LOG_INFO, "myplugin",
                    "created config section");
                break;
            case SC_CONFIG_APPENDED:
                api->log(SC_LOG_INFO, "myplugin",
                    "added missing config keys");
                break;
            case SC_CONFIG_ERR:
                api->log(SC_LOG_WARN, "myplugin",
                    "config_ensure failed, using defaults");
                break;
        }
    }

    // 2. Читаем настройки — они уже точно есть
    const char* model = api->config_get_string("model", "qwen3:4b");
    int timeout = api->config_get_int("timeout", 30);

    snprintf(g_model, sizeof(g_model), "%s", model);
    g_timeout = timeout;

    // 3. Проверяем зависимости (если объявлены в requires)
    if (api->abi_minor >= 4 && api->is_plugin_loaded) {
        if (!api->is_plugin_loaded("telegram")) {
            api->log(SC_LOG_WARN, "myplugin",
                "telegram not loaded, running in limited mode");
            g_has_telegram = 0;
        } else {
            g_has_telegram = 1;
        }
    }

    return SC_OK;
}
